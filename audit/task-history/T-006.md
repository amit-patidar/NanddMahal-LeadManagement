# T-006: Admin-created users and assigned-lead access

Date: 2026-08-19
Status: Done

## Request

Allow an administrator to add CRM users with a username and password, let each user log in, and show that user the leads assigned to them.

## Architecture review

The existing data model was a usable starting point because `users` already had identity, role, and active fields, and `leads.assigned_to` already referenced users. The original security model was not sufficient: passwords were plain text, the frontend stored authentication state in `localStorage`, request data could select the acting user, and lead filters were not server-scoped.

## Implemented design

### Authentication foundation

- Implemented Node `crypto.scrypt` password hashes with a random salt and constant-time verification.
- Implemented a server-side `sessions` table with random, expiring session tokens and an HTTP-only, SameSite cookie that is Secure in production.
- Protected API routes with authenticated session and admin checks. Acting user identity comes from the session, never request data.
- Implemented logout and active-user session invalidation.
- Removed `localStorage` authentication state.

### User and assignment management

- Implemented an admin-only Users page with create, deactivate, activate, and password-reset actions. Users are deactivated instead of deleted.
- Reused `leads.assigned_to` and added an admin assignment control for active users.
- Admins view all leads and sales users view only leads assigned to their session identity.
- Enforced sales lead scope on list, detail, update, and WhatsApp routes; admin-only APIs protect user management and sync.
- Assignment changes create an activity entry and do not change workflow status.

### Login and user experience

- Replaced the pre-login user dropdown with a username/email input and password field.
- Uses the existing `role` field for `admin` and `sales`.
- Added an admin-only Users navigation item.
- Admins set a temporary password; mandatory first-login password change is deferred and remains a follow-up decision.

## Decisions applied

1. Username means the existing unique email address.
2. Sales users see assigned leads only; admins see the full queue.
3. Administrators can reset passwords and deactivate or reactivate users; users are not hard-deleted.
4. Mandatory first-login password change is deferred from this release.

## Migration and verification

Before a production migration, export the current database. The local migration was verified against a rollback copy and then the local database. The isolated API QA script verifies both roles, assignment scope, URL-level denial, session revocation, logout, and unauthenticated rejection. See `audit/task-history/T-006-qa.md`.
