# T-008: Separate WhatsApp controls into a lead drawer

## Request

The current lead detail page places template sending, image selection, message history, direct replies, refresh controls, and failure information in the same vertical flow as lead details and activity. This makes the page feel crowded. Add a WhatsApp action beside the existing lead actions and keep WhatsApp work in a separate same-window surface.

## Team review

### Manager / product

- Keep WhatsApp available from every lead workflow where the signed-in user can access the lead.
- The WhatsApp action should be available beside `Open` and the existing call/update action in lead rows.
- The lead detail page should use the same action and open the same WhatsApp surface.
- Preserve the current WhatsApp capabilities: approved template selection, body parameters, header image selection/upload, message history, refresh, direct reply, and failure details.
- Do not create a second browser page or make the user lose the current list filters and scroll position.

### Architect

- Use a reusable right-side drawer/sheet in the current application shell.
- Keep drawer state at the app/page coordination level so it can be opened from either a list row or lead detail without duplicating WhatsApp logic.
- Reuse the existing WhatsApp endpoints and data model. No database migration is required for this UI change.
- The server remains the authority for lead access. The drawer must not rely on a client-supplied user ID to authorize requests.
- Keep one WhatsApp panel implementation. Refactor the current inline panel into drawer content instead of maintaining two copies.

### Frontend

- Use the local accessible WhatsApp brand mark because the existing icon library does not provide a WhatsApp brand icon. Add an accessible label and tooltip such as `Open WhatsApp`.
- On desktop, use a fixed right drawer with its own vertical scroll and a visible backdrop. Keep the underlying lead page visible and preserve its state.
- On mobile, use a full-width sheet or full-screen panel with the same close and scroll behavior. Prevent horizontal overflow.
- The drawer header should show the lead name, phone number, and a close button.
- Use a close button and Escape to close. Do not close on backdrop click in the first version so a partially written reply is not lost accidentally.
- Show loading, empty, permission, send failure, and retry states inside the drawer.

### Backend

- Reuse the existing protected routes for WhatsApp status, templates, media, messages, sending, and direct replies.
- Keep the existing 24-hour direct-reply rule and template parameter validation unchanged.
- Keep failure code/reason details available to the drawer.
- No new persistence structure is needed. Add a new endpoint only if implementation proves that the current endpoint sequence cannot provide the required drawer state.

### QA

- Test the drawer from every lead list and from lead detail for admin, manager, and sales roles.
- Verify list state, access control, template/media flows, message refresh, failure visibility, responsive layout, keyboard behavior, and all existing lead actions.
- Record screenshots or screen recordings for desktop, tablet, and mobile evidence during implementation.

## Decision

Implement a same-window right-side WhatsApp drawer. The list row action opens the drawer directly for that lead without navigating away. The lead detail action opens the same drawer. The current inline WhatsApp panel is removed from the normal lead-detail flow so lead information and activity are no longer pushed below a large messaging form.

The first version will keep the current backend contract and database structure. The drawer owns the selected lead context and refresh lifecycle, while the reusable WhatsApp content owns template, media, message, and reply controls.

## Interaction contract

1. A user clicks the chat/message icon beside a lead's existing row actions.
2. The drawer opens for that lead and displays the lead name and phone before any send control is usable.
3. Templates, media, message history, and WhatsApp status load for the selected lead. Each existing refresh action updates only the relevant drawer data.
4. Sending, direct reply, image upload, and failure details behave exactly as they do today.
5. Closing the drawer returns the user to the same page, filters, scroll position, and lead list state.
6. Opening another lead replaces the drawer context and cannot show messages or errors from the previous lead.
7. A lead that the server denies must not expose WhatsApp data, even if a client changes the lead ID in a request.

## Implementation boundaries

- Add drawer open/close state and a selected lead ID in the existing app flow.
- Add the WhatsApp action to lead rows and lead detail actions only where the user has access to the lead.
- Extract or reuse the current WhatsApp panel inside the drawer; do not duplicate its send logic.
- Keep API routes, database tables, Cloudinary behavior, Meta template behavior, webhook behavior, and 24-hour reply rules unchanged.
- Keep the existing call/update, comments, assignment, status movement, search, and list filter behavior unchanged.
